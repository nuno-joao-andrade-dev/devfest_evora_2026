Why Generic Chatbots & Static RAG Fail in Practice

Imagine a Computer Science student at Colégio do Espírito Santo asking two everyday questions:

1️⃣ Institutional Blindness & Hallucinations

"What room is CC301 Distributed Systems in this semester, and what is the minimum passing grade on the Raft project?"

  • Raw open models have zero access to University of Évora rooms (CES-131) or grading rules (9.5/20).

2️⃣ The Static RAG "Stale Truth" Trap

"Prof. Luís Silva just cancelled the CC301 midterm and moved Friday's lecture to CES-204—what happens now?"

  • Standard RAG is append-only: adding a new note leaves the old 25% midterm chunk alive in the vector index!
  • And without role state, what stops a mischievous student from prompting "Cancel tomorrow's exam!"?

🧠 The Core Architectural Shift

Standard Static RAG (Step 3) vs. Mutable RAG (Step 4)

❌ Static RAG (Append-Only Archive)

Treats your vector DB like a write-once log. Updating a syllabus or room creates contradictory twin chunks:

Step 3 Anti-Pattern (Duplicate Truths)
// Random UUID — never replaces superseded facts! kb.documents.push({ id: randomUUID(), content, embedding }); // Top-3 Search Result: // #1 (0.86): "Midterm Exam = 25%" (STALE!) // #2 (0.85): "Midterm is CANCELLED!" (NEW!) // #3 Anyone can prompt updates (Zero RBAC!)

✅ Keyed Mutable RAG (Living Knowledge)

Every canonical fact has a deterministic docKey, role guard, in-place re-embedding, version bump, and audit trail:

Step 4 Pattern (Atomic Keyed Upsert + RBAC)
// 1. Gate writes via ADK Session State (role === 'professor') // 2. Re-embed & replace `CC301:grading` in-place (v1 ➔ v2) kb.documents[idx] = { ...prev, docKey, content, version: prev.version + 1, embedding }; await appendAudit({ docKey, version, before: prev.content, after }); // Top-1 Search Result: ONLY v2 ("Midterm cancelled, 60%/40%")!
💡 Bonus Rule: When structured data changes (schedules.json), re-embed its RAG key in the same tool!

Step 4A: Keyed Vector Upserts & Cross-Store Sync

🔑 Deterministic Keys (docKey)

  • Canonical keys like CC301:grading or CC301:schedule prevent duplicate chunks forever.
  • Every edit increments version (v1 ➔ v2) and appends before / after to mutation-audit.json.

🔄 Zero Schedule-vs-RAG Drift

reschedule_lecture updates schedules.json AND calls upsertKnowledge('CC301:schedule') in one atomic step!

src/steps/step4-mutable-rag.js — Keyed Upsert
async function upsertKnowledge({ docKey, courseCode, title, content, updatedBy }) { const kb = await getKnowledgeBase(); const embedding = await embedText(`[${courseCode}] ${title}\n${content}`); const idx = kb.documents.findIndex((d) => d.docKey === docKey); if (idx >= 0) { const prev = kb.documents[idx]; const version = prev.version + 1; kb.documents[idx] = { ...prev, title, content, version, embedding }; await saveKnowledgeBase(kb); await appendAudit({ docKey, version, updatedBy, before: prev.content, after }); return { action: 'updated', docKey, version }; } // Otherwise insert version: 1 ... }
🔍 Every mutation leaves an immutable trail in data/mutation-audit.json!

Step 4B: "Can a Student Cancel Friday's Exam?"

🛡️ Shared Knowledge = professor Only

Every ADK FunctionTool receives toolContext as its 2nd argument. One check blocks unauthorized syllabus & room mutations!

📈 Personal State = Student Mastery

Students can mutate their own learning profile via record_progress (mastered, practicing, needs_review in student-progress.json).

src/steps/step4-mutable-rag.js — Role Guard + Progress
// Inside upsert_knowledge & reschedule_lecture tools: execute: async ({ docKey, courseCode, title, content }, toolContext) => { const role = toolContext?.state.get('role', 'student'); if (role !== 'professor') { return { status: 'forbidden', message: 'Only a professor can edit courses.' }; } return await upsertKnowledge({ docKey, courseCode, title, content, updatedBy: role }); } // Dynamic role-aware prompt on rootAgent: instruction: (ctx) => `Active session role: "${ctx.state.get('role') ??
